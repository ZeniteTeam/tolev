# Deploy do backend no Azure — registro de 12/09/2026

Registro do que foi feito na sessão em que o Phase 03 (App Service) saiu do
papel, para conferência posterior. Ordem cronológica.

## 1. Correções de infraestrutura antes de qualquer coisa

O `.env.azure` e o runbook diziam que o banco estava no resource group
`rg-tolev`, em Brazil South. **Os dois estavam errados.** Verificado com
`az group list` e `az postgres flexible-server list`:

| Registrado antes | Real |
|---|---|
| RG `rg-tolev` | RG **`tolev-pg`** |
| Brazil South | **Canada Central** |

Sem essa correção o Phase 03 morreria no primeiro comando, com
`ResourceGroupNotFound`. Corrigido em `.env.azure`: `RG=tolev-pg`,
`LOC=canadacentral`.

Decisão associada: **o App Service também vai para Canada Central**, colado no
banco. Separar as duas coisas colocaria um salto entre continentes em cada
ida ao banco, e uma requisição HTTP faz várias.

## 2. Banco religado e firewall

- Servidor estava em `Stopping`. O `start` é recusado no meio de uma parada:
  foi preciso esperar virar `Stopped` para então ligar. Estado final: `Ready`.
- **O IP residencial tinha mudado.** A regra de 28/08 apontava para
  `186.215.11.93`; o IP atual é `191.22.230.189`. Criada a regra
  `ClientIP-2026-09-12`. Isso só afeta rodar o backend na máquina local contra
  o Azure — o App Service entra pela regra
  `AllowAllAzureServicesAndResourcesWithinAzureIps_*`, que continua intacta.

## 3. Phase 02 refeito (checkpoint local) — verde

Rodado `scripts/azure/02-run-local-against-azure.sh` antes de gastar com
compute:

- Schema estava em **V13**; Flyway aplicou **V14 e V15** sem erro.
- Hibernate `validate` passou (o schema bate com as entidades).
- `Started TolevBackApplication in 19.24 seconds`, zero erro no log.
- `/actuator/health/liveness` respondeu `200 {"status":"UP"}`.

Era o risco real do deploy: se as migrations fossem quebrar, quebrariam aqui,
com o stack trace na tela, e não dentro de um container no Azure.

## 4. Correção no script do Phase 03

`az webapp create` falhou com:

```
ERROR: Linux Runtime 'JAVA|21-java21	2028-09-01	Linux	Java	Active	21' is not supported.
```

Causa: `az webapp list-runtimes -o tsv` devolve a linha inteira (runtime, fim
do suporte, SO, status...), e o script pegava a linha toda como se fosse só o
nome do runtime. Corrigido com `| cut -f1`; o fallback também passou de
`JAVA:21-java21` para `JAVA|21-java21`, que é o formato que esta versão da CLI
aceita. O plano B1 já tinha sido criado nessa primeira tentativa — por isso a
segunda execução pulou direto para o web app (o script é idempotente).

## 5. Phase 04 — front-end apontando para a nuvem

`TolevFront/src/api/axios.ts` não tinha como apontar para uma API remota: a URL
saía sempre do host URI do Expo. Agora:

```ts
const URL_DO_AMBIENTE = process.env.EXPO_PUBLIC_API_URL?.trim();
// dentro de resolveBaseUrl(), antes da dedução pelo Expo:
if (URL_DO_AMBIENTE) return URL_DO_AMBIENTE.replace(/\/+$/, "");
```

Com variável definida, fala com o Azure. Sem ela, o comportamento antigo
continua idêntico — desenvolver contra o backend local não mudou nada.

Arquivos novos:

- `TolevFront/.env` — gitignored, com a URL do App Service.
- `TolevFront/.env.example` — versionado, para quem clonar o repo.
- `TolevFront/eas.json` — perfis de build. O perfil `preview` gera **APK**
  (o padrão do EAS é AAB, que não instala direto no aparelho) e carrega
  `EXPO_PUBLIC_API_URL` no `env` do perfil. Isso é necessário porque o `.env` é
  gitignored e o EAS **não** sobe arquivo ignorado para o build — sem o `env`
  no perfil, o APK sairia apontando para `localhost`.
- `TolevFront/app.json` ganhou `android.package` = `com.zeniteteam.tolev`,
  obrigatório para qualquer build Android. **Vale revisar esse nome** — depois
  de publicado na Play Store ele não muda mais.

`npx tsc --noEmit` passou limpo.

## 6. Phase 03 — resultado

Recursos criados no RG `tolev-pg`, em Canada Central:

| Recurso | Nome | Detalhe |
|---|---|---|
| App Service Plan | `plan-tolev` | **B1 Basic**, Linux, ~US$13/mês |
| Web App | `tolev-api-zenite` | runtime `JAVA\|21-java21`, HTTPS-only |

Configuração publicada: `SPRING_PROFILES_ACTIVE=azure`, as três
`SPRING_DATASOURCE_*`, `JWT_SECRET`, `JWT_EXPIRATION`, `GEMINI_API_KEY`,
`GEMINI_MODEL=gemini-3.5-flash`, `JAVA_OPTS=-Xms256m -Xmx1024m` (teto de heap:
sem ele a JVM se dimensiona pelo host e leva OOM kill na B1). Sonda de saúde em
`/actuator/health/liveness`.

### Verificação feita depois do deploy

| Checagem | Resultado |
|---|---|
| `GET /actuator/health/liveness` | `200 {"status":"UP"}` |
| `GET /actuator/health` (inclui banco) | `200 {"status":"UP"}` |
| `GET /transactions` sem token | `401` com `{"status":401,...,"message":"Sessão expirada. Faça login novamente."}` |
| `POST /auth/login` com e-mail inexistente | `401` — prova que a consulta chegou ao Postgres |
| `npx expo export` + grep no bundle | a URL do App Service aparece no JS gerado — o `EXPO_PUBLIC_API_URL` está sendo embutido de verdade |

O corpo do 401 em português é a prova de que é o `SecurityConfig` deste
repositório respondendo, e não uma página de erro da plataforma.

**API no ar: <https://tolev-api-zenite.azurewebsites.net>**

## 7. O que falta / pontos para revisar

1. **`scripts/` continua fora do git** (untracked). É o único registro de como
   o deploy funciona — vale commitar.
2. **`android.package` = `com.zeniteteam.tolev`** foi escolhido por mim. Depois
   de publicado na Play Store esse identificador não muda mais.
3. **Para gerar o APK**: `npm i -g eas-cli`, `eas login`, `eas init` (grava o
   `projectId` no `app.json`) e `eas build -p android --profile preview`.
4. **`TolevBackApplicationTests` continua sem `@ActiveProfiles("test")`**, então
   `mvn test` ainda exige Postgres local. Não afetou nada aqui porque o deploy
   compila com `-DskipTests`, mas quebra qualquer CI.
5. **Custo**: ~US$31/mês (US$17,56 do Postgres + ~US$13 do App Service) contra
   o crédito restante. Parar o Postgres nas pausas continua sendo o único
   fôlego — mas atenção: **parar o web app não para a cobrança do plano**, só
   apagar o plano para.
