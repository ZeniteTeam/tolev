01Como revisar este documento

Toda constante numérica no motor recebe uma etiqueta de procedência. Ela existe porque a pergunta mais importante numa revisão deste tipo é de onde veio esse número — e a resposta honesta varia bastante.

Padrão Matemática estabelecida. Função logística, juros compostos, interpolação linear, valor esperado. Não há o que calibrar; ou está certo ou está errado.
Convenção Regra corrente de planejamento financeiro no Brasil: teto de 30% da renda para dívida, reserva de 6 meses de despesa. São heurísticas conhecidas, não leis.
Calibrado Meu julgamento. Não saiu de regressão sobre dados reais nem de literatura. É o que precisa da sua opinião de produto — e é o que mais influencia o que o usuário vê.
Derivado Veio do schema ou de código que já existia. Não é escolha nova.

A §09 apresenta um caso numérico — a usuária Marina — que é usado do §10 ao §14. Todo modelo termina com os números dela calculados passo a passo. Se você quiser entender o motor lendo uma coisa, leia esse rastro: ele conecta snapshot, notas, achados e recomendações num fio só.

Se o tempo for curto, os pontos de maior alavancagem são os pesos da saúde financeira, os coeficientes do modelo logístico e o portão de recomendação. A §22 lista o que eu mesmo considero frágil — inclusive três problemas que só apareceram quando rodei o caso da Marina no papel.

Escopo

A árvore de trabalho contém alterações anteriores a esta sessão — transação manual, categorias, amortização, migrations V11 e V12. Nada disso é meu e nada disso está descrito aqui. Este documento cobre exclusivamente o motor de análise e o que ele exigiu tocar.

02Decisão de arquitetura: um evento genérico

O CLAUDE.md especifica Spring Events como o mecanismo interno de comunicação, mas o código não tinha nenhum. Este é o primeiro, então ele define o padrão para todos os próximos.

O caminho óbvio seria um evento por ação — TransacaoCriadaEvent, PagamentoRegistradoEvent, DividaCriadaEvent. Recusei: com N eventos, cada tipo novo de análise obriga a mexer em todos os publicadores, e o módulo de finanças acaba tendo que saber quais análises existem.

shared/events/DadosFinanceirosAlteradosEvent.java

record DadosFinanceirosAlteradosEvent( Long idUsuario, // dono dos dados que mudaram OrigemAlteracao origem, // o fato que ocorreu String entidadeTipo, // "TRANSACAO", "DIVIDA", "USUARIO" — anulável Long entidadeId, // anulável LocalDateTime ocorridoEm )

Publicado dentro da transação de escrita, entregue depois do commit. O publicador não referencia o módulo de análise em momento nenhum — não há dependência de compilação entre eles. Duas fábricas estáticas: de(idUsuario, origem, tipo, id) e de(idUsuario, origem).

OrigemAlteracao classifica o fato e carrega um único comportamento: isAltoImpacto(), que decide se o recálculo fura a janela de debounce.

A lógica: uma despesa de R$ 30 pode esperar a janela fechar. Quitar uma parcela ou mudar a renda declarada muda o retrato inteiro, e o usuário está olhando para a tela esperando o número novo. Calibrado

analysis/events/FinancialDataChangedListener.java

@Async("analysisExecutor") @TransactionalEventListener(phase = AFTER_COMMIT) public void aoMudarDadosFinanceiros(DadosFinanceirosAlteradosEvent evento) { try { generateAnalysis.execute(evento.idUsuario(), evento.isAltoImpacto()); } catch (Exception e) { log.error(...); } }

AFTER_COMMIT garante que a análise nunca enxerga um lançamento que sofreu rollback. @Async tira o cálculo da thread da requisição — a análise varre até 180 dias de transações e pode chamar o Gemini. Como consequência, a exceção não tem mais para onde subir, daí o try/catch: uma análise que falha não pode aparecer como erro num POST que foi salvo com sucesso.

O pool é dedicado, separado do Tomcat: config/AsyncConfig.java — core 2, max 4, fila 100, DiscardPolicy. Descartar quando a fila enche é correto aqui porque cada execução recalcula tudo do zero: a próxima cobre o que foi descartado.

03Migration V13: identidade do achado

A regra de recorrência precisa responder "esse mesmo problema apareceu em quantos dias distintos?". Isso exige uma chave estável para o achado, e nenhuma coluna existente servia: tipo_impacto tem só cinco valores grossos (FINANCEIRO / META / DIVIDA / RISCO / COMPORTAMENTO), então "juros crescendo" e "parcela atrasada" na mesma dívida colidiriam na mesma chave.

db/migration/V13__add_regra_analise_recomendacao.sql

ALTER TABLE tb_analise_impacto ADD COLUMN regra VARCHAR(100); ALTER TABLE tb_recomendacoes ADD COLUMN regra VARCHAR(100); CREATE INDEX idx_analise_impacto_regra ON tb_analise_impacto (regra, entidade_origem_id); CREATE INDEX idx_recomendacoes_usuario_regra ON tb_recomendacoes (id_usuario, regra, status); CREATE INDEX idx_analises_usuario_tipo_data ON tb_analises (id_usuario, tipo, data_criacao);

Duas colunas aditivas e anuláveis, três índices. Nenhuma linha existente é reescrita e nenhuma leitura atual muda de comportamento. Os índices cobrem exatamente as três consultas que passam a rodar a cada evento: contagem de recorrência, deduplicação de recomendação e busca da análise do dia.

Interpolação por faixas — o coração do sistema de notas

Dado um vetor de fronteiras crescentes L = [l₀ … lₙ] e as notas correspondentes N = [n₀ … nₙ] (mesmo tamanho), para um valor v:

v ≤ l₀ → n₀ (piso) v > lₙ → nₙ (teto) v ∈ [lᵢ, lᵢ₊₁] → f = (v − lᵢ) / (lᵢ₊₁ − lᵢ) nota = nᵢ + f · (nᵢ₊₁ − nᵢ)

Padrão Interpolação linear entre pontos de controle.
Por que não degraus: 31% e 39% de comprometimento de renda não podem valer a mesma nota, senão o gráfico de evolução fica plano enquanto a situação piora — o usuário não veria nada acontecendo até cruzar uma fronteira.

Exemplo trabalhado — COMPROMETIMENTO_RENDA a 35%

L = {10, 20, 30, 40, 60} N = {100, 88, 68, 40, 0} v = 35 35 ≤ 10? não 35 ≤ 20? não 35 ≤ 30? não 35 ≤ 40? sim → i = 2, faixa [30, 40] f = (35 − 30) / (40 − 30) = 5/10 = 0,50 nota = 68 + 0,50 × (40 − 68) = 68 + 0,50 × (−28) = 68 − 14 = 54,00

Repare que N é decrescente aqui (menos comprometimento é melhor), então nᵢ₊₁ − nᵢ é negativo e a fórmula desce. A mesma fórmula sobe quando N é crescente. Não são dois casos — ver a nota abaixo.

Redundância que eu introduzi

Escrevi dois métodos, notaCrescente e notaDecrescente. Eles são algebricamente idênticos: nᵢ − f·(nᵢ − nᵢ₊₁) ≡ nᵢ + f·(nᵢ₊₁ − nᵢ). A distinção só existe para documentar a intenção no ponto de chamada. Não é bug — o comportamento está correto nos dois — mas é código duplicado e vale consolidar. Ver §22.

Formatação

formatarMoeda e formatarPercentual usam Locale.of("pt","BR") para produzir 1.234,50 e 30,5. Esses textos só entram no mapa dados dos achados, que preenche os templates — nunca em campo numérico do banco.

08AnalysisSnapshot: como os derivados são montados

…/service/AnalysisSnapshot.java (record) · …/service/AnalysisSnapshotAssembler.java (montagem)

Toda leitura passa pelas integration APIs. A análise nunca toca repositório de finance, progression ou users. Cada leitura é embrulhada num buscar() que devolve valor neutro em caso de falha: um módulo fora do ar não derruba a análise inteira — sem dívidas ainda dá para analisar consumo.

Renda: por que a declarada manda

rendaObservada = Σ (receitas de cada mês fechado com ≥1 lançamento) ───────────────────────────────────────────── nº desses meses nenhum mês fechado → usa o parcial do mês corrente rendaMensal = rendaDeclarada > 0 ? rendaDeclarada : rendaObservada

Calibrado (a precedência)
Por que a declarada manda: é a que o usuário usou para montar o orçamento dele — percFixos / percDividas / percLazer são percentuais dela. Usar a observada quebraria a coerência entre o teto que ele definiu e o teto que a análise cobra.
Por que só meses fechados: comparar um mês pela metade com meses completos sempre acusaria "ganhando menos". No dia 5, um mês parcial arrastaria a média para baixo em ~85%.

Categorias: o truque do id com sinal

idPorCategoria[nome] = idCategoriaGastoSistema (positivo) | −idCategoriaGastoUsuario (negativo)

tb_categorias_gastos_sistema e tb_categorias_gastos_usuario são tabelas distintas com ids independentes — o id 3 existe nas duas. Negar o id do usuário permite as duas conviverem numa chave só.
Por que isso importa: entidade_origem_id é o que distingue "delivery estourou" de "transporte estourou" na contagem de recorrência (§16). Sem essa chave, todas as categorias colapsariam num achado só e a recorrência ficaria sem sentido.

Comprometimento: o fallback

comprometimentoMensal = Σ valorTotal das parcelas pendentes cujo vencimento cai no mês corrente se der zero → Σ parcelaMinima das dívidas com saldo > 0

Calibrado
Mês sem parcela a vencer não significa dívida sem custo mensal — pode ser que a parcela vencia dia 5 e hoje é dia 20, ou que todas do mês já foram pagas. Sem esse fallback o comprometimento cairia a zero na segunda quinzena, o n₁ da saúde saltaria para 100 e o score subiria artificialmente todo mês — um serrote no gráfico de evolução que não corresponde a nada real.

Guarda de entrada

temDadosSuficientes() exige renda > 0 ou alguma transação ou alguma dívida. Abaixo disso o motor sai sem gravar nada — análise sobre zero é pior que análise nenhuma. Cada analisador tem ainda sua própria guarda: consumo exige transações, inadimplência exige dívidas.

10CONSUMO — padrão de gasto

…/analyzers/ConsumoAnalyzer.java · modelo CONSUMO_PONDERADO v1.0 · guarda: exige ≥1 transação.

Nota alta significa gasto sob controle: diluído entre categorias, estável mês a mês e deixando sobra.

score = Σ (pesoᵢ × nᵢ) Σ pesoᵢ = 1,00 coeficienteGeral = taxaPoupanca

As quatro variáveis

n₁ · TAXA_POUPANCA · peso 0,35

valor bruto = 100 × (rendaMensal − despesaMensal) / rendaMensal pp L = {−20, 0, 10, 20, 30} N = { 0, 30, 60, 85, 100}

O que mede: quanto da renda sobra depois das despesas correntes. Não desconta parcelas de dívida — isso é medido separadamente pelo comprometimento.
Convenção A referência de 20% vem da fatia de poupança da regra 50/30/20. Calibrado O mapeamento 20% → nota 85, e todo o resto do vetor. Note que a faixa começa em −20%: gastar 20% a mais do que ganha zera a nota, e piorar além disso não piora mais.

n₂ · DESPESA_SOBRE_RENDA · peso 0,25

valor bruto = 100 × despesaMensal / rendaMensal pp L = { 50, 70, 85, 100, 120} N = {100, 80, 55, 30, 0}

Por que junto com n₁ se são complementares? São correlacionados mas não idênticos: n₁ é a sobra, n₂ é o consumo. Ter as duas com pesos diferentes (0,35 e 0,25) é uma forma de dar peso total 0,60 ao mesmo eixo econômico com curvas de penalização distintas — a de poupança pune mais o déficit, a de despesa pune mais o gasto alto mesmo com renda alta. 22Problemas conhecidos

Não verificado — o mais importante

O contexto Spring nunca foi carregado contra um banco real. Compilei e rodei os testes unitários (31/31 passando), mas não subi a aplicação. Duas coisas seguem sem prova: as duas consultas @Query em IAnaliseImpactoRepository, que o Hibernate valida na inicialização e não na compilação; e se a V13 aplica limpo. Rode contextLoads contra o Postgres antes de confiar.

Bug de projeto — score-drivers

GetScoreDriversGraphService calcula contribuiçãoMáxima = peso × 100, assumindo que peso é fração de uma média ponderada. Vale para CONSUMO, SAUDE_FINANCEIRA e RISCO. Não vale para INADIMPLENCIA, onde peso guarda o coeficiente logístico (2,40 → "máxima" de 240), nem para PREVISAO, onde todos os pesos são 1. O endpoint não quebra — devolve números — mas os números não significam nada nesses dois tipos. Opções: restringir o endpoint aos três tipos ponderados, ou separar "peso" de "coeficiente do modelo" em colunas distintas.

Dupla contagem no impact-ranking

Os R$ 612 de delivery da Marina entram duas vezes no custoAnualTotal: como excedente de categoria (R$ 2.784) e como gasto de vendedor (R$ 7.344). Somam R$ 10.128/ano para o que é, na prática, R$ 612/mês de delivery. Pior, os dois números têm semânticas diferentes — um é excesso sobre a média, o outro é gasto total, e CONCENTRACAO_EXCESSIVA_CATEGORIA usa uma terceira (gasto total da maior categoria). O ranking por item continua útil; o total é enganoso.

Calibragem — o logístico parece agressivo

Marina tem poupança positiva (27,5%), zero atrasos, comprometimento exatamente no teto convencional — e recebe 57,91% de chance de atraso. O que carrega o resultado é x₃ (ausência de reserva) valendo 0,9512 e contribuindo 1,28 dos 3,07 pontos acima do intercepto. Ter pouca reserva é de fato um fator de risco, mas o modelo hoje trata "sem reserva" quase como "já atrasando". Sugestões: baixar b₃ de 1,35, ou suavizar a normalização (saturar em 3 meses em vez de 6 muda a curva bastante).

Sem teto de recomendações por execução

No terceiro dia, Marina recebe 7 recomendações de uma vez — todas legítimas, todas bem acima do limiar. Nenhum código limita quantas podem ser criadas numa execução nem quantas podem ficar PENDENTES simultaneamente. Sete cartões de alerta de uma vez é o tipo de coisa que faz o usuário ignorar todos. Vale considerar um teto por execução (ex.: as 3 de maior impacto) ou um teto de pendentes.

Duplicação e simplificações
  • notaCrescente ≡ notaDecrescente — algebricamente idênticos (§06). Consolidar elimina ~15 linhas e a chance de alguém "corrigir" um dos dois.
  • Custo de não ter reserva usa juros simples (0,08 × 12) onde o rotativo é composto. Subestima em ~60%.
  • mesesParaQuitar ignora juros. Para Marina dá 9 meses; com 12% a.m. no cartão o número real é bem maior.
  • Projeções × 12 não descontam a valor presente. Consistente em todo o motor, mas não é o custo econômico exato.
  • n₁ e n₂ do consumo medem eixos correlacionados (sobra e gasto) e juntos pesam 0,60. Defensável, mas um revisor pode chamar de dupla contagem.
Fora de escopo

O AnaliseTab do app continua com dados mockados. Ligá-lo a GET /analysis e aos novos gráficos é trabalho separado, não incluído aqui.
